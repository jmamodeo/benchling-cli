# API limitations

These limits are based on the public Benchling documentation and OpenAPI contracts. The document, unstructured-table, and entry-field portions were rechecked against the V3 spec captured on 2026-11-19.

- The V3 Document API is beta. This client sends `EARLY-ACCESS: true` and uses the unified `/api/v3` routes.
- Entry content is an ordered, flat list. Sections are derived from section markers; they are not independent nested resources.
- Unstructured-table reads return `rows` as a URL. This client pages `.../rows/items` at `pageSize` 100, the maximum the API accepts. `set_cells` sends `update_table_cells` and `append_rows` sends `insert_table_rows` on `PATCH /entry/{id}`. There is no full-table replace.
- Those cell and row writes reset table evaluation (`isEvaluated` becomes false). Benchling's browser recalculates formulas.
- `DocumentPartResultsTable` parts are readable, including typed columns and paged rows. Their cells are not editable here. Registration, inventory, and other structured tables are still not readable or editable through the document API. `DocumentPartUnavailable` parts are reported as unavailable rather than kept as an unknown type.
- `benchling results rows` and the MCP tool `list_results_table_rows` read one page from `GET /document-part-results-table/{id}/rows/items`. `pageSize` is 1 to 100 and defaults to 50. `nextToken` resumes the following page. The part is loaded first, and its `rows` URL must be that path on the same tenant. `entry get --full` still reads every row of the part.
- `benchling export` and the MCP tool `export` do not call a Benchling export endpoint. They page the existing reads: unstructured-table rows at `pageSize` 100, results-table rows at `pageSize` 100 until `nextToken` is absent, and assay results from `GET /result/items` at `pageSize` 100. The rows are written to a local JSON or CSV file. The response is a summary (row count, column names, path, SHA-256) and does not include the rows. A cell is the evaluation when Benchling returned one, otherwise the input. An existing file is not replaced unless overwrite is set. Nothing is written to Benchling. `--part` for `table` and `results-table` is a `v3_document_part` id (`docpart_…`) from `entry inspect`. `results tables` returns `v2_structured_table` ids (`strtbl_…`). `export --kind results-table --part strtbl_… --entry ENTRY` resolves that id through the entry's document parts, or reads assay results for the entry and the table's result schema when no results-table part matches. A `strtbl_…` id without `--entry`, or with `--kind table`, is a validation error that names `v3_document_part`. V3 result measurements are `schemaFields` (field-definition id plus `BenchlingValue`), not a V2 `fields` map. Assay-result export adds one column per field, named with the field definition's display name. Link values, including results-table and unstructured-table cells, are the linked ids. An unset result field is empty (`""` in CSV, `null` in JSON). `linkedEntityId` is omitted when it is the result's own id or the field is not a link.
- Document insert uses `position`, delete uses `sourceRange`, and move uses `sourceRange` plus `destinationPosition`. A part ID means immediately before that part. A move that would leave the entry starting with anything other than a section fails in preview with `Entry must start with a section`, before a plan is saved. These mutations and unstructured table updates send the entry version from `versionMetadata.versionId` and return HTTP 409 when it is stale. Entry schema-field updates do not publish an equivalent atomic version precondition. This client compares affected values immediately before writing and labels that protection as best effort.
- Entry field inputs may use a V3 field `systemName` or its field-definition ID. Plans show both and send the field-definition ID (`tsf_…`), which is what `schemaFields` accepts. V2 result uploads still use the result field's `systemName`. Display names are rejected there because they are mutable and may not be unique. A V3 result update resolves a mapped CSV column to a field-definition id and sends that id.
- `changes plan --family results --csv` reads a CSV file. `--id-column` names the result id (export writes `id`). Each `--map CSV_COLUMN=FIELD` is required; columns are not inferred. `FIELD` may be the export display name, the system name, or the field-definition id. Unknown columns, ambiguous names, and bad rows are one validation error and nothing is written. Unmapped columns are left unchanged. A blank cell clears a value that is present. A blank cell on an empty field is not a change: export writes both null and an empty string as a blank cell, so an unmodified export does not clear those fields. The plan stores each result's `modifiedAt` and the mapped values. Apply re-reads every result and sends `PATCH /result/{result_id}` only when those still match. `UpdateResultInput` has no version property, so `modifiedAt` is the version precondition. The body is `schemaFields` keyed by field-definition id. The limit is 500 rows. A later PATCH failure leaves earlier PATCH results in the journal as partial completion.
- Replacing a text part requires insert followed by delete. If the second request fails, the entry contains both parts and the journal reports partial completion.
- Results created through the API land as pending. Benchling's V3 guide says: "When results are created in this way, they are not immediately appended to the destination table. Their source is marked as "pending" and they will not appear in the table until they are explicitly integrated." A person integrates them with the plug icon in the table toolbar. The same holds for V2 `assay-results:bulk-create` with a `tableId`, so this is not specific to one API version. The public V2 and V3 specs have no call that accepts pending results. The accept control may insert every pending result that matches the table's schema, so avoid stray or test results. Results created without a table id are not attached to a table at all. After an upload, `changes apply` returns `next_step` telling the user to accept the results in the named table.
- Live verification on 2026-09-29 against a Benchling tenant found that it rejects `assayResults[].id` in notebook-table bulk uploads, even though public V2 `AssayResultCreate` declares it. The CLI omits remote IDs, retains local correlation UUIDs plus task IDs, and never treats those local UUIDs as idempotency keys. Fresh plans are required for the updated contract; plans using the old request shape cannot be applied. Table uploads are capped at 500 records.
- Current V3 document-part responses are flattened `DocumentPart*` objects. Reads preserve these objects and support both flattened and legacy nested content. Unknown types are explicitly retained as opaque data. V2 get responses wrap their object (for example `entry`, `project`, `folder`); adapters unwrap and validate these instead of silently reporting empty data. Tasks can be flat status objects without IDs. Confirmed task result IDs are persisted by `changes status` for reconciliation.
- Pending result uploads have no entry (`entryId`/`entry` is null) until a person accepts them in the table. A CSV update of such a result is refused with "Result is not on the selected entry", and the message says to accept the pending results first. After a result is accepted, `PATCH /result/{id}` changes the result record. A live check on a development tenant found that the notebook results-table cell still showed the old value afterward, so re-read the result, not the table cell, to confirm an update. An Entry Link schema-field value is a distinct relationship and does not make the pending result appear in the V3 `entry.eq` filter. Read pending records by the canonical V3 IDs returned in the task instead.
- A result plan verifies its `strtbl_…` identifier against the selected entry's V2 `results_table` note, enforces that note's result schema, validates required fields, and checks supplied project IDs. Those reads do not establish write permission; Benchling remains authoritative at submission time.
- A write that times out is never retried automatically. Its journal status is `unknown` until reconciled.
- Plans are guarded by per-plan cross-process locks, so a CLI and MCP process cannot intentionally apply the same plan concurrently. A plan with any prior attempt is not reusable.
- Full entry reads combine entry metadata, document parts, schemas, V2 entry fields, and result records from several calls. The client reads the entry version before and after assembly, but linked results do not share that atomic document version; their independent retrieval timing and page count are reported separately.
- Attachment metadata and temporary download URLs may be returned. Attachment binaries are not downloaded by `entry get --full`.
- Authentication is app client credentials, one saved environment at a time (`benchling auth login --env NAME`, optionally `--tenant-url`, `--client-id`, and `--secret-stdin`). The tenant URL is normalized (bare host, trailing slash, or a trailing `/api/v2` or `/api/v3`); `http://` is rejected. The tenant URL and client ID are stored in `environments.json`; the client secret is stored in the OS keychain, with no plaintext fallback. On Linux that keychain is Secret Service on the session bus, and the MCP client must pass `DBUS_SESSION_BUS_ADDRESS` because the SDK's default environment does not. Every CLI command and MCP tool call names its environment explicitly. App permissions, not the browser user's permissions, control API access. The Benchling app must be granted access to specific projects. Personal keys, delegated login, and saved profiles are not supported.
- Benchling's official Python SDK currently targets V2. This package uses HTTPX for both API versions.
- V3 `GET /entry/items` applies `project.eq`, `schema.eq`, `name.anyOf` (exact, case-insensitive, not a substring), and inclusive `modifiedAt.gte` / `modifiedAt.lte`. It has no folder parameter. Live tenants ignore `folderId` on that route, so this client does not send it. A folder filter sends the whole query to V2 `GET /entries`, where `folderId`, `projectId`, `schemaId`, `names.anyOf`, and `modifiedAt` are server-side together. A name that contains a comma cannot be one item of `name.anyOf` or `names.anyOf`: both are comma-separated and the contract documents no escape. That name is sent as V2 `name`, with the other filters on the same V2 query. V2 `name` is a single entry name. The contract describes it as the specified name and does not say the comparison is case-insensitive. Nothing in an entry list is filtered in the client. A bare date is the start or end of that UTC day. A timestamp must include a time zone; a value with no zone is rejected. V2 documents `>` and `<` comparisons; this client sends `>=` and `<=` so the bounds stay inclusive. Listing `modified_at` values are UTC timestamps with a `Z` suffix. V2 responses that use `+00:00` are rewritten, and other offsets are converted to UTC.
- Schema lists page through `/entry-schema/items`, `/result-schema/items`, and `/run-schema/items`. The caller's page defaults to 50 and stops at 100 so a large tenant is not returned in one response. Dropdown options come from `/dropdown/{dropdown_id}` and the unpaginated `/dropdown/{dropdown_id}/options/items`. The deprecated dropdown-option list is not used.
- Each apply journal event stores the raw HTTP status of that write. A failure that never produced an HTTP response has no status.
